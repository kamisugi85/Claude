# Claude一次評価ガイド（Scout）

`prepare` が出力した `scout/data/<date>/pending_eval.json` の各案件を評価し、
`merge --evals <file>` に渡すJSON配列を作る。本人プロフィールは
`python3 scout/pipeline.py show-profile` で確認する（リポジトリには置かない）。

## 原則
- 本人作業時間あたりの期待純利益（Expected Net Profit ÷ Human Minutes）を最重視する。本人の作業は1日5〜10分と最終確認が目標。
- 案件名だけで候補にしない。`desc`（募集本文）で必須条件・稼働・納期・AI条件を確認する。
- プロフィールにない経験・資格・執筆歴・商品の利用歴は絶対に創作・推定しない。Webライター、SEO、WordPress、校正の経験は「未確認」として扱う。
- 実務経験（例：金融）と、そのテーマの記事執筆経験は別物として扱う。
- 本人の体験が必要な案件
  - プロフィールにある経験の範囲なら「要確認」とし、本人への質問を最大3問つける。
  - プロフィールにない経験なら「除外」にする。
- AIで回答を作ると虚偽の回答やレビューになる案件（アンケート、口コミなど）では、AIに回答を作らせない。
- 評価0の発注者は、それだけでは除外しない。リスクとして記録する。

## AI利用条件（ai_condition）
- A: AIによる文章生成まで明示的に許可（「丸投げ・そのまま納品NG」の条件付きを含む）
- B: 参考・補助としての利用のみ許可 → AIによる全文生成を前提に作業時間を見積もらない
- C: 記載なし・不明 → AIを使えると決めつけない
- D: 禁止 → 除外

## 分類（classification）
- A: 超短時間Task（5〜100円程度）
- B: AIレバレッジ（400〜8,000円程度が目安。価格帯で機械的に限定しない）
- C: Professional / Human Premium

## 出力スキーマ（1案件=1オブジェクト）
```json
{
  "job_id": 12345678,
  "classification": "A|B|C",
  "ai_condition": "A|B|C|D",
  "requirements": ["必須条件を本文から列挙"],
  "fit": "適合|要確認|不適合",
  "profile_link": "本人プロフィールとの接点",
  "ai_steps": ["AIで処理できる工程"],
  "human_steps": ["本人が行う工程"],
  "ai_completion": "85-90%",
  "human_minutes": "3-5分",
  "est_hourly": "約4,000-7,000円（推定）",
  "repeatability": "高|中|低",
  "client_risk": "低|中|高（理由）",
  "user_questions": ["最大3問。不要なら空配列"],
  "verdict": "候補|要確認|除外",
  "reason": "判定理由",
  "source_notes": "報酬の実額・締切など原文確認メモ",
  "gross_jpy": 3000,
  "lane": "Auto|Professional|Experience|Human Premium"
}
```
- `gross_jpy`：一覧の予算表示と本文の実単価が違う場合に、本文の1件あたり報酬（税込）を入れる。想定手取額はこの値から手数料20%を引いて計算される。
- `client_risk`・`reason` にクライアントの数値を書くときは、`client_history` / 公開値のラベルどおりに書く（「Scout検知の他募集N件」「CW公開：募集実績N件」「当方の納品N件」は別物）。ある項目の数を別の項目（例：他募集27件→「納品27件」）に言い換えない。意味が分からない数は書かない。`app-merge` は応募文・回答の、Claude QAは一次評価の、記録と合わない実績数を検出する。
- 初回テストと継続で報酬が違う場合、今回の応募に適用される報酬は `app-check` が原文から `initial_reward` / `ongoing_reward` に分ける（RUNBOOK 4.7）。`gross_jpy` の意味は従来どおり。
- Auto案件（データ収集・データ入力・転記・PDF/Word/Excel変換・分類・要約・リライト・リスト作成・Web調査など）の `human_minutes` は、人が手で作業した場合の時間ではなく、AI・スクリプト・ルール処理の後に本人が行う確認時間を書く。自動取得が規約上・技術上できない場合（会員ログインが必要なサイト、スクレイピング禁止の明記、手入力指定）はその前提で見積もる。本人経験が不要でも、AI・自動処理で95%以上完結するならAuto候補として残す。
- `lane`：Auto（AI・自動処理の後に本人が確認するだけ）／Professional（本人の職務経験・専門知識が価値）／Experience（本人の体験・属性が必要）／Human Premium（本人の判断・対人・創作そのものが価値）。`runs.jsonl` の `lane_mix` に集計される。
- Autoはテキストに限らない。AI-BPO（tier E）などの、生成AI・AI画像生成・Canva（無料版）・AI動画・資料やスライドなどのAI補助制作も、既存契約のAI・無料枠・規約上許される自動化で本人作業を小さくできるならAuto候補として評価する。`human_minutes` は生成後の確認・修正・納品の時間で見積もる。有料ツールの追加契約が必須、本人の撮影・出演・音声が必要、AI生成禁止、大量の手作業、規約違反となる自動化、継続的な大きい本人拘束は、減点または除外する。応募設問で生活状況や将来の理想の働き方を尋ねる募集は、勧誘の兆候として扱う。
- 本人拘束の大きい案件（電話営業・架電、長時間Zoom・定例会議、即レス・平日日中の常時対応、大量の本人手入力、AI利用禁止、規約上許されない自動取得、SNSのDM・フォーム営業の送信作業）は、報酬が高くても減点または除外する。
- `human_minutes` には、AI処理の後に本人が成果物を確認・修正する時間（今回契約分）を書く。応募・本人入力・契約・修正対応期待値・納品操作の時間は `pipeline.py` が加えて期待本人総時間（`human_minutes_total`）にし、ENP÷Human Minutesとtierに使う。分からない作業量は推測しない（数値が書けなければ空にする→UNKNOWN）。
- AI条件が書かれていない（C）ことだけを理由に「要確認」にしない。機密・個人情報を外部AIに入れずに遂行できるかで判断する。守秘義務の記載がある案件は、原文を外部AIサービスに投入しない前提（ローカル処理・本人確認）で見積もる。
- 作業時間と時給は推定値として書く（「推定」と明記する）。受注後の実測値が集まると `pending_eval.json` の `calibration`（実測÷予測の比率）に反映されるので、次回以降の推定を補正する。
- `候補` と `要確認` はAstra Queueに入る。`除外` はJob Masterに記録され、Astra Queueには入らない。
